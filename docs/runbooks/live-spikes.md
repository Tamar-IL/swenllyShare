# Live-Spikes Runbook — the four P0 checks

**Owner:** backend-engineer (integrations). See `docs/05-kickoff-brief.md` "First P0 spikes"
for why these four exist, `docs/design/architecture.md` §9/§12 for the honesty-ledger
mechanism this runbook feeds, and `docs/research/05`/`08` for what's already known vs.
guessed about each provider.

**Ground truth for this document:** as of this write-up, **zero live calls have been made to
Google Drive, Zoho WorkDrive, or Mailgun by anyone on this project.** Every method on
`GoogleDriveShare`, `ZohoFileStore`, `MailgunInboundAdapter`, and `MailgunOutboundAdapter`
carries an `@unverified-live` marker (`docs/verification-ledger.md`, generated by `pnpm
gen:ledger`). This runbook is how that changes, one method at a time, without ever letting the
ledger say something happened that didn't.

**The one rule that keeps the ledger honest:** don't flip `@unverified-live` → `@verified-live(YYYY-MM-DD)`
on a method until *you personally* watched it complete against the real provider in this
run. Flip only the methods you actually exercised — a spike that only calls `upload` and
`createPublicLink` does not get to mark `revokeLink` or `delete` verified too, even though
they're "probably fine." Then run `pnpm gen:ledger` (no `--check`) and commit the regenerated
`docs/verification-ledger.md` alongside your code change — CI's `pnpm gen:ledger --check`
fails the build if the committed file doesn't match what the markers actually say.

Every spike below is a **manual, credentialed run** — none of it happens in CI, and none of
it happens automatically. Nothing here requires code changes to `src/adapters/**` unless the
run surfaces a wrong assumption (see "If it fails" under each spike) — the whole point of
building the adapters first is that a live run is a *configuration* exercise.

## Spike 1 — Zoho WorkDrive: public link + chunked upload on the paid plan

**Confirms/denies:** `research/05 §2`'s single open question ("does the WorkDrive API need a
paid plan?" — the founder holds one, per the kickoff brief, but nobody has called the API
yet), the `POST /upload` and `POST /links` request shapes, the `role_id` mapping (default
`ZOHO_LINK_ROLE_ID=6`), and — if you have a file over 250MB handy — the large-file
`uploadlargefile` session shape, which is the single most speculative piece of code in this
codebase (see the doc comment on `ZohoFileStore.uploadLargeFile`).

**Env vars needed** (fill from a real WorkDrive OAuth client — see Zoho's API console under
your account, "Self Client" or "Server-based Application" for a refresh token):

```
LIVE_ZOHO=1
ZOHO_CLIENT_ID=...
ZOHO_CLIENT_SECRET=...
ZOHO_REFRESH_TOKEN=...
ZOHO_TEAM_FOLDER_ID=...          # a real WorkDrive folder id you can write into
ZOHO_API_BASE=https://www.zohoapis.com/workdrive/api/v1   # or your DC's equivalent — see below
ZOHO_ACCOUNTS_BASE=https://accounts.zoho.com               # switch DC if your account isn't global
ZOHO_LINK_ROLE_ID=6
```

If your Zoho account is on the EU/IN/AU/CN/JP data center (check the URL you log into
WorkDrive with), `ZOHO_ACCOUNTS_BASE` and `ZOHO_API_BASE` both need the matching host
(`accounts.zoho.eu` / `.in` / `.com.au` / `.com.cn` / `.jp`, and the WorkDrive API host on the
same DC) — getting this wrong produces a token or 401 error that looks like a bad credential,
not a wrong data center (this exact trap is called out in the adapter's own config comment).

**Command:**

```
scripts/dev-db.sh start
export TEST_DATABASE_URL="$(scripts/dev-db.sh url | grep TEST_ | cut -d= -f2-)"
LIVE_ZOHO=1 pnpm test:integration tests/contract/file-store.test.ts
```

(`test:integration` because `tests/contract/**` runs inside the vitest "integration"
project — see `vitest.config.ts` — but `TEST_DATABASE_URL` isn't actually needed for this
particular file; the DB setup file just warns and continues without it if unset.)

**What counts as pass:** the `FileStorePort contract: real` describe block runs (not
skipped — check the console for the "LIVE_ZOHO is not set" warning **not** appearing) and its
one test passes: upload → create-link → download round-trips the same bytes → revoke → delete,
with no thrown error. Watch the terminal for the actual `url`/`embedToken` your account
returns — paste them into your spike notes, since `extractOrDeriveEmbedToken`'s fallback path
(deriving a token from the plain link's last path segment) needs the log-in checked: did the
`POST /links` response actually contain an `embed_url` field, or did the adapter fall back to
the derived guess? That answer is one of the most important facts this spike can produce
(`research/08 §1a`).

**If it also has a file over 250MB:** temporarily point `MAX_UPLOAD_BYTES`/a manual script at
`ZohoFileStore.upload` with a >250MB stream to exercise `uploadLargeFile`. Expect this to
fail or need adjustment — the whole method is a modeled guess (its own doc comment says so).
Whatever the real shape turns out to be, fix `uploadLargeFile` to match, not the other way
around.

**What to record:**
1. Flip `@unverified-live` → `@verified-live(YYYY-MM-DD)` on exactly the methods you ran:
   typically `upload`, `createPublicLink`, `openDownload`, `revokeLink`, `delete` — leave
   `uploadLargeFile`'s comment (it's not a separate ledger entry; `upload` covers both paths,
   so only mark it verified once you've actually exercised a file above 250MB).
2. Run `pnpm gen:ledger` and commit `docs/verification-ledger.md`.
3. Update the `role_id` comment in `src/adapters/zoho/real.ts` if the observed mapping
   differs from `5=edit/6=view/7=upload`, and update `ZOHO_LINK_ROLE_ID`'s default in
   `.env.example` if `"6"` wasn't actually the view-only value.
4. If the response carried a genuine `embed_url` (or any other confirmed embed-token field),
   delete the "derive from the plain link" fallback comment's uncertainty language — it's no
   longer a guess for this API version, but wire the confirmed field name in
   `extractOrDeriveEmbedToken` first.

## Spike 2 — Google Drive: visitor sharing + reactive auto-duplication on the quota error

**Confirms/denies:** whether the central account (service account + domain-wide delegation,
or a personal Gmail via `oauth_refresh`) actually lets a non-Google-account recipient open a
privately-shared file via email-OTP visitor sharing (`research/05 §1`, `advisor-consult.md
§4`); the *actual* 403 `errors[].reason` string Drive returns when the sharing velocity limit
is hit (this codebase assumes `sharingRateLimitExceeded` / `rateLimitExceeded` /
`userRateLimitExceeded` — a kickoff-brief-specified set, never independently observed); and
the resumable-upload chunk framing against a real Shared Drive.

**Env vars needed** (service-account mode — the advisor's recommended path,
`advisor-consult.md §4`):

```
LIVE_GOOGLE=1
GOOGLE_CREDENTIAL_MODE=service_account
GOOGLE_SA_JSON_PATH=/path/to/service-account.json
GOOGLE_IMPERSONATE_SUBJECT=someone@yourworkspace.com   # domain-wide delegation target
GOOGLE_SHARED_DRIVE_ID=...                             # a real Shared Drive id
GOOGLE_ROOT_FOLDER_ID=...                               # optional — a folder inside it
```

Or, for the founder-fork path (no Workspace — `advisor-consult.md §4`, PRD §10.4):

```
LIVE_GOOGLE=1
GOOGLE_CREDENTIAL_MODE=oauth_refresh
GOOGLE_OAUTH_CLIENT_ID=...
GOOGLE_OAUTH_CLIENT_SECRET=...
GOOGLE_OAUTH_REFRESH_TOKEN=...
```

**Command:**

```
LIVE_GOOGLE=1 pnpm test:integration tests/contract/drive-share.test.ts
```

**What counts as pass:** the `DriveSharePort contract: real` block isn't skipped, and its
test passes end to end (upload → copy under an intent key → `findByIntent` recovers the copy
→ share a permission to a real email you control → revoke → delete both Drive objects).
**Then, manually** (this part isn't automatable — it needs a second human/device):
1. Share to an email address that has **no** Google account.
2. From that address's inbox, open the sharing notification (or construct the file URL) on a
   device not signed into any Google account, and confirm the email-OTP visitor-sharing
   prompt appears and works. This is the AC-R4 "no Google account" path — record whether it
   actually worked, degraded (e.g. blocked outright), or wasn't offered at all. If it's
   blocked, that's the founder-fork conversation from `advisor-consult.md §4` re-opening, not
   a code bug.
3. If you can safely do it without burning a real customer relationship: share the same test
   file to ~50–100 throwaway addresses in a loop and watch for the actual 403 to occur, and
   record the exact `errors[].reason` string in the response body. Compare it against
   `QUOTA_REASONS` in `src/adapters/google/real.ts`. This is the single highest-value fact
   this whole runbook can produce, because `SharingEngine`'s entire reactive-duplication
   design (architecture.md §5) depends on catching the right string.

**What to record:**
1. Flip `@unverified-live` → `@verified-live(YYYY-MM-DD)` on the methods you ran:
   `uploadResumable`, `copy`, `findByIntent`, `sharePermission`, `revokeAll`, `delete`.
2. Run `pnpm gen:ledger` and commit `docs/verification-ledger.md`.
3. If the observed 403 reason string differs from `QUOTA_REASONS`, **fix the code first**
   (add/correct the reason string in `src/adapters/google/real.ts`), re-run, then mark
   verified — never mark a method verified against behavior the code doesn't actually match.
4. Write the visitor-sharing manual-test outcome into `docs/progress.md` (CLAUDE.md §7-style
   lesson if it's a genuine surprise, since AC-R4's whole story depends on it) — this doesn't
   belong in the ledger (it's not a port method), but it's the fact the PRD §10.4 founder
   fork is waiting on.

## Spike 3 — Mailgun: per-file inbound addresses with a real DMARC result

**Confirms/denies:** the entire guess in `src/adapters/mailgun/mapping.ts` — which field
name(s) actually carry the DMARC/SPF/DKIM verdict in a 2026 Mailgun Routes payload
(`research/05 §3` cites a 2026 Mailgun release note promising this, but nobody has seen a
real payload); the webhook HMAC signature scheme against a real, delivered request; and the
full file-request → private-share round trip end to end.

**Env vars needed:**

```
LIVE_MAILGUN=1
MAILGUN_API_BASE=https://api.mailgun.net       # or api.eu.mailgun.net for the EU region
MAILGUN_API_KEY=...
MAILGUN_SIGNING_KEY=...                         # from the Mailgun dashboard, NOT the API key
MAILGUN_SENDING_DOMAIN=mail.yourdomain.com
OUTBOUND_FROM="Swenlly <no-reply@mail.yourdomain.com>"
LIVE_MAILGUN_TEST_RECIPIENT=you@somewhere-you-control.example   # see warning below
# Optional for this spike's first run — leave unset to exercise the INBOUND_DOMAIN
# fallback default; set once you know the real authserv-id from step 3b's capture.
MAILGUN_AUTHSERV_ID=...
```

**⚠️ `OutboundMailPort`'s real leg actually sends an email.** Set
`LIVE_MAILGUN_TEST_RECIPIENT` to an address you control before running it — the default
fallback (`contract-test@example.com`) is deliberately a non-deliverable placeholder so an
accidental run without this var set doesn't spam a real inbox.

**Commands — run these in order, they build on each other:**

```
# 3a. Outbound send — the simpler half, no webhook infrastructure needed.
LIVE_MAILGUN=1 LIVE_MAILGUN_TEST_RECIPIENT=you@example.com \
  pnpm test:integration tests/contract/outbound-mail.test.ts
```

```
# 3b. Inbound signature verify — needs Mailgun to actually deliver a webhook, which needs
# either a public URL (ngrok/a real deployment) or Mailgun's own webhook test/replay tool
# in the dashboard pointed at your sandboxed domain's Route.
#   1. Set up a Mailgun Route: match_recipient("^cust-.*@<your-domain>$") -> forward to a
#      URL you control (e.g. an ngrok tunnel to a local `pnpm dev` instance, or a real
#      staging deploy's /webhooks/mailgun/inbound). Leave `INBOUND_REQUESTS_ENABLED=false`
#      (the F-1 kill switch, default true — set it false here on purpose) pointed at that
#      deployment until this spike confirms the field-name guess below: with it off, every
#      signature-verified webhook is quarantined (reason `inbound_disabled`) instead of
#      being evaluated against a still-unconfirmed DMARC gate, so a live test message can't
#      accidentally auto-share a file on a wrong guess while you're still capturing payloads.
#   2. Send a real email to cust-abc123+file-<any26charstoken>@<your-domain> from an
#      address whose domain has SPF+DKIM+DMARC configured (Gmail/Workspace works).
#   3. Capture the FULL raw payload at the webhook route (temporarily add a debug log in
#      webhook-mailgun.ts, or read it back from `inbound_messages.raw_payload` — the
#      pipeline stores it for RAW_PAYLOAD_RETENTION_DAYS regardless of outcome, including
#      quarantined, so step 1's kill switch doesn't cost you the capture). Look specifically
#      for:
#        - a top-level `message-headers` field (Mailgun's documented JSON array of every
#          MIME header) — does it exist on your plan/route config? If so, does it contain
#          an `Authentication-Results` entry, and does that entry's authserv-id (the part
#          before the first `;`) match a real, stable hostname you can put in
#          MAILGUN_AUTHSERV_ID? Also check whether there is more than one
#          Authentication-Results entry (a forwarding hop) and confirm the TOPMOST one is
#          genuinely the one your own receiving MTA added, not a passed-through one.
#        - failing that, any top-level field that plausibly carries the DMARC/SPF/DKIM
#          verdict directly (this is the `mailgun-fields` source in mapping.ts) — record
#          its EXACT name and casing.
LIVE_MAILGUN=1 pnpm test:integration tests/contract/inbound-mail.test.ts
```

**What counts as pass for 3a:** the `OutboundMailPort contract: real` block isn't skipped,
both its tests pass, and the email you designated actually arrives with the expected subject/
body/attachment.

**What counts as pass for 3b:** you have a captured raw payload from a real delivered
message and can answer, definitively: *does `message-headers` exist and carry a real
`Authentication-Results` entry, what authserv-id does it report (for `MAILGUN_AUTHSERV_ID`),
and what DMARC value format does it use (`pass`/`fail`/`none`/something else entirely)?* The
`inbound-mail.test.ts` contract suite passing only proves `verify`/`parse` behave consistently
with the fake — it does **not** prove the auth-results extraction in `mapping.ts` is correct,
because `parse()` is a pure function over whatever payload you hand it. It is only actually
confirmed by inspecting a **real captured payload** against
`src/adapters/mailgun/mapping.ts`'s doc comment (the `(a)`/`(b)` source description) and
`MAILGUN_AUTHSERV_ID`'s default (falls back to `INBOUND_DOMAIN` in `container.ts` — confirm
whether the real authserv-id actually matches that, or needs setting explicitly).

**What to record:**
1. Flip `@unverified-live` → `@verified-live(YYYY-MM-DD)` on `send` once 3a passes and the
   email is confirmed delivered.
2. `verify`/`parse` are trickier: only mark them verified once you've run `verify` against a
   **real** signature (not the fake's self-signed one) and confirmed `parse` extracts the
   correct DMARC value AND the correct evaluated domain (`dmarcDomain`, gate 6's alignment
   check) from a **real captured payload** — not just that the contract suite's synthetic
   payload round-trips.
3. Run `pnpm gen:ledger` and commit `docs/verification-ledger.md`.
4. **If the real payload's auth-results shape differs from `mapping.ts`'s `(a)`/`(b)`
   sources** (e.g. `message-headers` doesn't exist on your plan, or the real authserv-id
   doesn't match `MAILGUN_AUTHSERV_ID`'s `INBOUND_DOMAIN` fallback, or the DMARC verdict
   lives under a field name `mailgun-fields` doesn't check), this is the most consequential
   fix in the whole spike list: update `src/adapters/mailgun/mapping.ts` (its extraction
   functions, not by adding back guessed Title-Case/`X-Mailgun-*` candidate names — see its
   doc comment for why those were removed) and/or set `MAILGUN_AUTHSERV_ID` explicitly, then
   re-run, and only then mark verified AND flip `INBOUND_REQUESTS_ENABLED` back to `true` on
   the deployment(s) this was tested against. Shipping the wrong shape here means the DMARC
   gate (architecture.md §4.5, pipeline gate 5) is permanently `'unknown'` for every real
   message and **every legitimate request gets silently quarantined** — this is the single
   highest-severity unverified assumption in the whole adapter layer, which is exactly why
   `INBOUND_REQUESTS_ENABLED` exists as a no-deploy-needed way to hold the path shut until
   this spike is done.
5. Append a `docs/lessons.md` entry per CLAUDE.md §7 if the real field name/shape surprised
   you — this is exactly the kind of fact that should never need re-discovering on the next
   project.

## Spike 4 — White-label whitelisting: does a Zoho embed render inside a real filter?

**Confirms/denies:** `research/08 §1a`'s two-part risk — whether `swenlly.com` itself, and
separately the `workdrive.zohoexternal.com` embed subdomain, are viewable from a device behind
a real whitelist-mode filter (NetFree/Rimon/Netspark). This spike is explicitly **"when
ready"** in the kickoff brief, not a build blocker — `BRANDED_PAGE_ENABLED` defaults to
`false` and the raw Zoho public link (already filter-proof per the founder's own prior spike)
is the shipping default regardless of this spike's outcome.

**Nothing in `src/adapters/**` needs credentials for this one** — it needs Spike 1 done first
(a real Zoho public link + embed token to test with), `BRANDED_PAGE_ENABLED=true` on a
reachable deployment, and physical/remote access to a device already running one of the
filter products.

**Command:** none — this is a manual browser test, not an automated one.

1. Finish spike 1 far enough to have a real `zoho_embed_token` for a test file.
2. Deploy (or run locally with a tunnel) with `BRANDED_PAGE_ENABLED=true`.
3. From a device genuinely running NetFree (or Rimon/Netspark), navigate to
   `https://swenlly.com/s/<slug>` (or your test domain). Record:
   - Did the page itself load at all? (Tests whether `swenlly.com`/your test domain needs
     separate whitelisting.)
   - If the page loaded, did the `<iframe src="https://workdrive.zohoexternal.com/embed/...">`
     render, or did it show as a blocked/blank frame? (Tests the embed subdomain
     specifically — `research/08 §1a`'s point that a whitelisted `workdrive.zoho.com` public
     link does **not** imply `workdrive.zohoexternal.com` is also whitelisted.)

**What counts as pass:** both the page and the iframe render on the filtered device. A
partial result (page loads, iframe blocked, or vice versa) is still a useful, recordable
outcome — it is not a pass/fail for the *build*, since `BRANDED_PAGE_ENABLED` stays `false`
by default regardless.

**What to record:** this isn't a `src/adapters/**` port method, so there's nothing to flip in
the verification ledger. Record the outcome in `docs/progress.md` and, if either domain needs
a whitelisting request filed with the filter vendor, track that as a founder-facing follow-up
(per architecture.md §12 item 1) — it's an external process this team doesn't control, not an
engineering task.

## After any spike: the honesty-ledger checklist

1. Only flip markers for methods you personally watched succeed against the real provider,
   this run, with credentials that actually belong to a live account.
2. `pnpm gen:ledger` (no flags) to regenerate `docs/verification-ledger.md` from the markers.
3. `pnpm gen:ledger --check` to confirm it matches (this is what CI runs).
4. Commit the code changes (if any) and the regenerated ledger in the same change — the
   ledger drifting from the code it describes is exactly the failure mode this mechanism
   exists to prevent (architecture.md §9).
5. Update this runbook's env-var list if you discover an additional variable was needed that
   isn't already in `.env.example` — the goal is that the *next* person's first live run is
   still "fill in the values," never "read the adapter source to reverse-engineer what's
   needed."
