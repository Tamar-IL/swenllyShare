# Lessons Ledger — Swenlly System 2 (File Sharing)

The self-improving loop (CLAUDE.md §7): a failure caught by a reviewer becomes a one-line
regression lesson here, and future work is checked against it. Seeded with the load-bearing
findings from Discovery so the build never re-learns them the hard way.

| Date | Caught by | Symptom | Root cause | Rule that prevents it |
|---|---|---|---|---|
| 2026-09-07 | AI Red Team | Auto-sharing a file because an email "asked" trusts the `From:` — spoofable | Email `From` has no cryptographic guarantee without DMARC alignment | Verify DMARC on every inbound trigger; share only to the verified sender's own address; rate-limit per sender/file; audit log. |
| 2026-09-07 | PM / Trust & Safety | Auto-subscribing on an inbound email risks ₪1,000/msg (Israeli spam law) and poisons deliverability | Adding to the sendable list before consent is confirmed | Double opt-in by default: inbound "הצטרפות" → reply-to-confirm ("כן") → then add + consent log. Never blast before confirm. |
| 2026-09-07 | AppSec | Full-inbox OAuth would trigger Google CASA ($$/yr) and make a breach expose the owner's whole inbox | Reading the customer's personal mailbox for "listening" | Listen via per-customer addresses on our own domain (Mailgun), not personal-inbox OAuth. If customer files ever need OAuth, scope Google to `drive.file` (CASA-free). |
| 2026-09-07 | Architect | White-label "Swenlly page" would be blocked for filtered users | Filters gate at the domain before the page loads; an unwhitelisted parent page never renders (iframe never runs) | Raw Zoho public link is the default filter-passing path; the branded embed page ships behind a flag, OFF until swenlly.com (and the zohoexternal embed domain) are whitelisted. |
| 2026-09-07 | Backend spike | Google's ~350/file share limit is not a fixed number | It's an undocumented, velocity-based anti-abuse trigger | Don't hard-code 350: detect the quota error and duplicate the file + swap the ID reactively, with margin. |
| 2026-09-08 | AI Red Team | Requester adds `X-Mailgun-Dmarc-Result: pass` to their own email and the DMARC gate opens — full auth bypass (`tests/redteam` RT-01/RT-05) | Mailgun posts the message's own MIME headers as top-level webhook parameters, and `mapping.ts` probes that same flat namespace for DMARC/SPF/DKIM — attacker-controlled and provider-asserted data share one namespace | Never read a security decision out of a namespace the attacker can write to. Allowlist the provider's synthetic field names and discard the rest of the payload before mapping; confirm the real field name against a captured live payload before the gate goes live. |
| 2026-09-08 | AI Red Team | DMARC alignment silently not checked in production (RT-02) | `if (msg.dmarcDomain && ...)` — an unreadable field means "skip the check" instead of "refuse". `dmarc` fails closed on the same uncertainty; `dmarcDomain` fails open | A guard whose input is optional must fail closed. If a control's input is missing, quarantine and alarm — never treat absence as satisfaction. |
| 2026-09-08 | AI Red Team | `<victim@corp.test@attacker.test>` passes an `@corp.test` allowlist and is mailed to attacker.test (RT-04) | The domain used for the check is `split('@')[1]` (first segment); the domain mail is delivered to is the last segment | Validate an email address to a single well-formed mailbox before any gate reads part of it, and derive the domain from the LAST `@`. Check-value and use-value must be the same value. |
| 2026-09-08 | AI Red Team | Expired and deleted files are still mailed out; a job retry mails the file twice (RT-10..RT-13) | Authorisation gates run at request time; `delivery.fulfill` runs minutes-to-hours later and re-checks nothing, and sends before it records | Re-evaluate every authorisation gate against fresh state at the moment of the external side effect, and make the side effect at-most-once (mark `sending` before the call, treat `sent` as done on retry). |
| 2026-09-08 | AI Red Team | Expiry revokes nothing: `file.expire`, `staging.purge`, `inbound.purge` are never enqueued by any production code path (RT-50..RT-54) | Handlers were built and unit-proven; the scheduling that invokes them was never written, and the integration test enqueued the job by hand — so the test passed while the control did not exist | A test that arranges its own trigger proves the handler, not the control. Every scheduled job needs a test that asserts the *scheduling*, and a `readyz` check that the recurring jobs exist. |
| 2026-09-08 | AI Red Team | `mallory+1@…`, `mallory+2@…` multiply the per-requester rate budget without limit; one attacker domain exhausts a file's whole hourly budget and silently denies real recipients (RT-30/RT-31) | The bucket key is the raw address string, and there is no per-domain bucket | Normalise rate-limit keys to the identity you actually mean to limit (strip sub-address tags), and always add a bucket one level up (domain) so a single actor cannot consume a shared budget. |
| 2026-09-08 | AI Red Team | 25 MiB of unauthenticated multipart body is fully buffered, then answered 401 (RT-40) | The body parser runs before the HMAC gate, and neither `bodyLimit` nor multipart `limits` are set on the route | Authenticate before you buffer. Any public endpoint gets an explicit body cap, and the cheapest rejection must come first. |
| 2026-09-08 | Backend Engineer (fixing F-5) | A job scheduled from a future point on the injected `Clock` (`file.expire` at `expires_at`) never became claimable no matter how far a test's `FakeClock.advance()` moved virtual time | `jobs.claimNext`'s "is this due" check compared `run_after` against Postgres's real `now()`, which a `FakeClock` (frozen except on explicit `advance()`/`setTo()`) cannot move | Any code that compares a scheduled time against "now" must compare against the SAME clock the schedule was computed from. When a real clock and an injected one must coexist (ordinary jobs default to real time; a few compute `run_after` from the injected `Clock`), compare against `max(injected clock, real time)` rather than picking one — it degrades to real-time comparison automatically whenever the injected clock hasn't been deliberately advanced past it. |
| 2026-09-08 | Critic | A single transient Mailgun error permanently drops a file delivery and records it `sent` (`reason: 'ack_lost'`); the job's whole retry budget is dead code for the outbound call | The at-most-once CAS treats one state (`dispatching`) as "the provider may already have it", conflating a *definite* non-send (5xx/429/DNS — the common case) with an *ambiguous* one (request written, no response — the rare case it was designed for) | An at-most-once guard must distinguish "definitely not sent" from "possibly sent", and only the second may finalize without retrying. Pass the provider a deterministic idempotency key so the ambiguous case stops needing a guess. "No pinned test requires it" is a description of a test gap, not a reason. |
| 2026-09-08 | Critic | F-1 was reported fixed in four documents, but the DMARC gate is still forgeable in three of four realistic payload shapes — the degraded fallback validates *less* than the primary path, and the anti-forgery guard is derived from a field (`message-headers`) that may simply be absent | A fix conditional on an unverified property of a third party was written up as unconditional; the priority order also lets a possibly-attacker-supplied source outrank the provider's own | When a fix depends on a precondition you have not verified, the artifact must state the *property that now holds and its precondition*, never just the change that was made — and the code must fail closed when the precondition is missing. A guard whose input can be absent is not a guard. |
| 2026-09-08 | Critic | `tests/integration/branded-page`'s AC-U3 leak assertion passes only because the fake's embed token is deliberately unrelated to the public URL, while the real adapter's documented fallback derives it from that URL's last path segment | The fake encoded a *hoped-for* property of an unverified external API rather than the range of shapes it may actually return, so the test proved the fake, not the requirement | A semantic fake must model the provider's worst realistic behaviour, not its most convenient one. When a real adapter has a fallback path, the fake must be able to produce that path's output too — otherwise the AC's proof evaporates exactly when the fallback fires. |
| 2026-09-08 | Critic | A kill switch built specifically because an authentication mapping is unverified defaults to ON, is absent from `.env.example`, and is unmentioned in the production checklist | The mitigation was designed for the operator who reads the security ADR, not the operator who copies the example env file and follows the runbook | A safety flag guarding an unverified assumption defaults to the safe position and is turned *on* by the spike that verifies it. Any config var not in `.env.example` and the deploy checklist does not exist operationally. |
| 2026-09-08 | Backend Engineer (fix pass 5, F-C) | `tests/integration/jobs.test.ts`'s `ensureScheduled` reactivation test failed intermittently (~1 in 5 runs) after adding `run_after = EXCLUDED.run_after` to its `DO UPDATE` | Stamping `run_after` from Postgres's `now()` and comparing it moments later against a caller-supplied `new Date()` (`claimNext`'s default) races real clock skew between the app process and the database server — a race invisible in a single run and only sometimes visible under repetition | A "was this reactivated correctly" check does not need to also re-stamp the schedule to *right now* — only touch a scheduled time when the caller actually supplies a new one (`COALESCE(explicit value, existing column)`), never default to a fresh `now()` a moment before comparing it against a different process's clock. Run a new/changed SQL-timing-sensitive test several times, not once, before trusting it green. |
| 2026-09-08 | Critic (re-check) | The DMARC gate was re-fixed and re-documented as closed, but an attacker can still assert their own `dmarc=pass` — by naming the configured `MAILGUN_AUTHSERV_ID` (Mailgun's public MX hostname, not a secret) in their own `Authentication-Results` header, or by adding a MIME header named `Dmarc:` that makes the anti-forgery guard discard Mailgun's genuine verdict and fall through to the weaker source | The fix's threat model assumed a public identifier was secret, and its dedup guard fails OPEN into a second source whose input the attacker also controls — so the attacker chooses which source answers | Before shipping a guard, name the exact secret it depends on and prove it is one; a hostname in your own MX record never is. And a guard whose input the attacker can poison must fail closed for the WHOLE decision — never fall through to a second, weaker source. Corollary for tests: a negative test must forge the *currently configured* value, not the value the previous version used, or it pins the old bug's absence instead of the new fix's presence. |
| 2026-09-08 | Critic (re-check) | Fixing a false-`sent` outcome produced an honest-but-terminal `unconfirmed` outcome that is counted nowhere, alarmed nowhere and cannot be resent — so a routine deploy restart mid-delivery silently drops a file | Replacing an optimistic guess with an honest "unknown" is only half the fix; an unknown that nothing observes is operationally identical to a loss | When a fix converts a wrong answer into "we don't know", the same change must make "we don't know" *visible and actionable* — a counter on the health endpoint, a badge on the affected object, and an operator action to resolve it. Honesty without a surface is still silence. |
| 2026-09-08 | Critic (re-check) | Forged `Authentication-Results` naming Mailgun's own hostname was accepted; a junk `Dmarc:` MIME header switched the gate to a weaker source (C′/C″/F) | An authserv-id is a public hostname, not a secret; "try source A, fall back to B" lets the attacker choose which source answers | A security verdict comes from exactly ONE operator-chosen source, chosen after observing the provider live; classify each source as absent/ambiguous/present before use; any ambiguity or disagreement fails closed; state the residual that only a live check can settle. |
| 2026-09-08 | Critic (2nd re-check) | The DMARC gate counts `Authentication-Results` entries to decide "one = trust it, two = forgery" — but a genuine stamp written in either of the two other spellings RFC 8601 permits (`host 1; …` version token, `host (comment); …` CFWS) is not counted, so the attacker's forged copy becomes the unique match and beats Mailgun's own `dmarc=fail` | The parser was written against one example of the header rather than against the RFC's grammar, and the *safety property* ("two entries ⇒ ambiguous") was built on top of that parser rather than on top of the protocol | When a security decision counts occurrences of a protocol element, parse that element by its specification's grammar, not by the one example you have seen — every unparsed legal form is an entry the attacker gets to delete from your count. And any runbook step that verifies such a property must assert the *system's outcome*, never the operator's reading of the raw data. |
| 2026-09-08 | Critic (2nd re-check) | Two sources are cross-checked for agreement on the DMARC verdict but not on the evaluated domain, so the authoritative source's attacker-chosen `header.from` is accepted verbatim while the other source's genuine domain sits unread in the same payload | The cross-check was written around the field the finding named (`dmarc`), not around every field the downstream gate actually consumes — gate 6 aligns on `dmarcDomain`, which no cross-check covered | A cross-source consistency check must cover every field a downstream gate reads, not just the field that motivated the check. Enumerate the consumers of the extracted value and check what they use. |
| 2026-09-08 | Critic (2nd re-check) | Third consecutive pass in which the README and the decisions log describe a security design that the current fix pass deliberately deleted, while the progress log and red-team report were correctly updated | Doc updates are done per-fix by whoever remembers, so the documents nearest the fix get updated and the founder-facing ones drift; there is no list binding "this invariant" to "these documents" | Every security invariant gets a named owner-list of documents, and changing the invariant means editing all of them in the same commit — treat a stale security claim as a failing test, not a typo. The template that works: state the property, its precondition, then the residual, in that order (`red-team-report.md` §6 F-1). |
